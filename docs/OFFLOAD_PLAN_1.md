# Surfaces — Workload Offload Plan (Workers ↔ grimmauldplace)

## Overview

Evaluate which Surfaces workloads should move from Cloudflare Workers to `grimmauldplace` (home server: 2013 MBP, 8GB RAM, 98GB SSD, Ubuntu 24.04, Docker stack with Caddy + cloudflared, Tailscale). Optimize for: keeping the public showcase stack (`/api/*`, MCP, OAuth, per-minute polling) untouched, while moving heavy ETL and headroom-sensitive jobs to a box where CPU and memory aren't billed by the millisecond.

This is a **plan**, not an implementation. No code, no docker-compose, no migrations. Read, push back, then we decide what (if any) milestone to take first.

The pre-decided constraints from the user's prompt are not re-litigated:

- Public API (`/api/*`) stays on Workers.
- Per-minute polling stays on Workers.
- OAuth flow + MCP server stay on Workers.

Everything below assumes those four points are fixed.

## 2. Per-candidate architecture proposals

### 2.1 Heavy ETL on `streams.feather` (recommended: move)

**Status quo:** `data/streams.feather` (260,790 rows, 15 years) lives on the laptop. Derived files (`track_affinity.csv`, `lost_favorites.csv`, `monthly_top.csv`, `companions.json`, `ip_geo.json`, `dashboard_data.json`) are generated by Python scripts on the laptop. These are committed into the repo and read at runtime by the Worker via embedded JSON or by the ingest script. Live-sync into D1 happens on Workers (`syncRecentPlays` in `src/listening/sync.ts`).

**Architecture on grimmauldplace:**

- Container: `etl` — Python 3.12 + pandas + pyarrow. Build from a small Dockerfile in `~/stack/etl/`.
- Storage: bind-mount `~/stack/etl/data/` → `/data` inside the container.
  - `streams.feather` (read-only canonical copy — copied from laptop once, then live-sync extends it)
  - `derived/*.csv`, `derived/*.json` — written by the container
  - `tail.feather` — incremental new plays from Spotify recently-played, unioned at read time per the LISTENING_HISTORY.md "Live API and snapshot freshness" section
- Trigger: a host cron (not docker cron — host cron is more debuggable) at 2:00am ET. Picks late-enough that the Worker's `0 5 * * *` cron has finished writing its day's data into D1, but `tail.feather` doesn't depend on D1 — it pulls from Spotify directly via `recently-played`. The two paths are independent.
- Spotify auth: this is the first cross-runtime token-sharing question. **Two options**, see §3.1.

**Where do the derived files go?**

Three places, each for a different reason:

1. **`~/stack/etl/data/derived/`** on grimmauldplace — canonical. The container writes here.
2. **The Worker** continues to read the embedded `eras.json`, `never_stale_core.json`, `companions.json`, `ip_geo.json` from the repo as today. These are stable enough that a manual `git commit` after a refresh is fine — the embedded versions move on a release cadence, not nightly.
3. **D1 `plays` table** — already populated (see existing `PLAN.md`). Live-sync continues on Workers, unchanged. The ETL container doesn't write to D1 in this design.

**This is the key simplification:** the ETL container is a *batch processor*, not part of the request path. Workers don't depend on it being up. If grimmauldplace is offline for a week, derived files just don't refresh — the Worker keeps serving from the last-committed embedded versions. Acceptable.

**Failures noticed via:** Uptime Kuma already exists. Add a small "heartbeat" file the ETL container writes after each successful run. Uptime Kuma monitors that file's mtime via a tiny HTTP endpoint (see §3.5).

### 2.2 Constellation rebuild (recommended: move compute, push results to D1)

**Status quo:** `0 10 * * *` cron on Workers. Just hit D1 CPU timeouts twice. Even after the recent fixes, headroom is thin. The rebuild reads `plays`, `track_taste`, and `artist_taste`, computes the graph, and writes it back to D1 (or, plausibly, to KV as a single blob — the project has both options open). `/api/constellation` reads the result.

**Architecture on grimmauldplace:**

- Container: `constellation-builder` — Node 22 + better-sqlite3, OR Python + sqlite3, OR plain TypeScript on bun. Pick whichever the user is most comfortable with; the algorithm doesn't care. Best instinct: **TypeScript with the existing `src/constellation/` code reused as much as possible**, run via `tsx` or compiled with esbuild. Reasoning: the current rebuild logic is already written in TypeScript and tested. Rewriting in Python doubles the maintenance burden for no win.
- Trigger: host cron `0 10 * * *` (same time as today's cron — the public API stops getting served stale data).
- Data flow:
  1. Container fetches `plays`, `track_taste`, `artist_taste` from Cloudflare D1 via the **D1 HTTP API** (Cloudflare exposes a REST endpoint per database; auth is a Cloudflare API token scoped to D1:Edit). This is the load-bearing primitive that makes the whole offload pattern work — see §3.2.
  2. Compute the constellation locally. No CPU limit, no subrequest budget.
  3. Write the result back to D1 via the same HTTP API in a single `INSERT OR REPLACE` (or, if the result is large and only-blob-shaped, write it to KV via the Cloudflare API).
- The Worker's `0 10 * * *` cron is **deleted**. The `/api/constellation` endpoint reads from the same D1/KV location as before — it has no idea the rebuild moved. This is the desired property.

**Why D1 HTTP API and not, say, a write-back webhook to the Worker?**

- A webhook means the Worker has to expose an authenticated `POST /admin/constellation/result` endpoint that accepts a potentially-large payload, validate it, and write it. That's a lot of new attack surface for a single workload.
- The D1 HTTP API is already-existing, scoped, and rate-limited by Cloudflare. The container has a token; the token can write to D1; that's it. Smaller blast radius.
- Cost: D1 HTTP API counts against the same D1 billing buckets, so no additional charges.

**Trade-off being eaten:** the daily cron now depends on grimmauldplace being up at 10:00 UTC. If the home server is off or the home internet is down at that exact minute, the rebuild silently doesn't run. The constellation will go stale — but `/api/constellation` keeps serving yesterday's result. The website shows old data, not no data. Acceptable for a 24-hour-stale cap; **alarming if it goes 7+ days** because that's a sign nobody's watching. See §3.5.

**Failures noticed via:** ETL heartbeat pattern. Last successful rebuild timestamp goes into a Worker KV key (`constellation:last_rebuilt_at`); a Worker route `/api/health/constellation` returns staleness; Uptime Kuma pings that route and pages on > 36-hour staleness.

### 2.3 Taste rebuild + acoustic backfill (recommended: defer)

**Status quo:** `0 5 * * *` block in the Worker's `scheduled()` handler. Sequence: live-sync recent plays → derive → rebuild taste model → rebuild affinities → audio features backfill → acoustic profile rebuild → prune.

This is currently the single longest cron the Worker runs. It hasn't timed out (yet), but the constellation rebuild already taught us how thin the margin is. So why defer rather than move?

**Three reasons to leave it alone, for now:**

1. **It's not the one that's bleeding.** The constellation is. Move that first, see if the daily cron's CPU usage drops enough to give the taste rebuild back its headroom organically.
2. **It writes to ~6 different D1 tables.** Moving it to grimmauldplace turns each of those writes into an HTTP-API round trip. The constellation-rebuild migration writes to one table (or KV). Different beast.
3. **The slow part isn't CPU — it's ReccoBeats.** Audio backfill is rate-limited at 40/day per project_status. That's a network-bound job, not a compute-bound one. Moving it to a beefier CPU does nothing useful. The right fix for backfill, *if backfill is the pain*, is to bump the batch size and run more often — and that's a Workers config change, not an offload.

**When to revisit:** if the daily 1am ET cron starts hitting CPU limits *after* the constellation rebuild has been moved off, then we know it's the taste rebuild itself that's the problem, and we move it using the §2.2 pattern. Until then, churn for no benefit.

**One small thing worth doing now, regardless:** profile the 1am cron. Add timing logs around each phase (sync, derive, rebuild taste, rebuild affinities, backfill, profile, prune). Lets us see where the seconds go.

### 2.4 Discovery agent (recommended: defer, bundle with #2 once pattern is proven)

**Status quo:** `0 10 * * *` cron. Five RSS feeds (Hype Machine, Stereogum, Line of Best Fit, EARMILK, Gorilla vs Bear, Aquarium Drunkard — one per day on a 5-day rotation), Last.fm similar-artist API for top-6 seed artists, Spotify search to resolve titles to URIs, dedup against `track_taste`/`play_events`, write to `fresh_pool`.

**Why offload would help:**

- Ditches regex-based RSS parsing for a real parser (`feedparser` in Python or `rss-parser` in Node). The OPEN_QUESTIONS file already flags this: "RSS title parsing is regex-based — fails safely (unparseable items skipped)." A real parser increases the discovery yield from each feed.
- Five feeds + Last.fm + Spotify search adds up to a non-trivial subrequest count on Workers; offloading buys back budget.
- Reddit-based discovery, which is currently deferred because regex won't handle it, becomes feasible.

**Why defer:**

- The discovery agent isn't bleeding. Constellation is. Don't move two things at once or you can't tell which one broke.
- The constellation move proves the pattern (host cron → D1 HTTP API → write back). Once proven, discovery is a copy-paste of the same pattern with different code.

**When to move:** after constellation has run on grimmauldplace for a week without incident. Then move discovery as `Migration #2`.

### 2.5 D1 backup / weekly export (recommended: move as part of #1)

**Status quo:** Not implemented. The original plan flagged "export D1 to a local file weekly. Add a simple `/admin/export` endpoint behind Cloudflare Access." Never built.

**Architecture:**

- New container in `~/stack/etl/` (or just a host cron line, no container needed): `wrangler d1 export spotify-agent-db --local` weekly, written to `~/stack/etl/backups/spotify-agent-db-YYYYMMDD.sql.gz`.
- Retain last 12 weeks (3 months). Older snapshots roll off via a `find -mtime +84 -delete`.
- Uptime Kuma monitors the most recent backup file's mtime (same heartbeat pattern as #1).

**Why bundle with #1:** same container infrastructure, same monitoring pattern. Adds maybe an hour of work on top of the ETL container, and gets the backups that should have existed already.

**Off-site:** if you want an extra layer, a daily `rclone copy` to Backblaze B2 or a Cloudflare R2 bucket. Cheap; zero code; out of scope for the first migration.

### 2.7 Lyrics + credits backfill (implemented: 2026-05-02)

**Status:** Container built and deployed as `stack/lyrics-backfill/`. This was the first workload actually migrated to grimmauldplace, built on top of Step 0's D1 HTTP API validation.

**Architecture on grimmauldplace:**

- Container: `lyrics-backfill` — Node 22 + tsx@4. Three phases invoked via subcommand: `isrc`, `lyrics`, `credits`.
- D1 access: via HTTP API (shared `lib/d1.ts` with retry/backoff), same pattern as `stack/hello/`.
- Spotify access (ISRC phase only): via Worker-side token broker (`POST /admin/spotify-token`), protected by Cloudflare Access service token. Refresh logic stays on Workers; grimmauldplace never sees the refresh token.
- Trigger: manual one-shot (`docker compose run lyrics-backfill <phase>`). Optional catch-up cron deferred to a follow-up.
- Coverage at start: 570/47,593 ISRCs cached (1%), 9 tracks with lyrics/credits (~0%). Full bulk job needed.
- Time estimates: ISRC ~30 min, lyrics ~3 hours, credits ~28 hours.

**Worker-side change:** `POST /admin/spotify-token` added to `src/index.ts`. Returns `{ access_token, expires_at }`. No refresh token in response. Protected by Cloudflare Access `/admin/*` application with service-token auth.

**What this proved:** the Spotify token broker pattern from §3.1 option 1 works. The D1 HTTP API pattern from §3.2 scales beyond hello-world to real workloads. Both are reusable for subsequent container migrations.

## 3. Cross-cutting ops + risk

These apply to any of the moves above. Grouped because solving them once unlocks the rest.

### 3.1 Spotify token sharing across two runtimes

This is the one that bites. Right now: Spotify OAuth refresh tokens live in Cloudflare KV under `tokens.ts`. The Worker reads them, refreshes when needed, and writes the new access token back. Atomic.

Once a second runtime (grimmauldplace) wants to make Spotify API calls (for live-sync extension in #1, for any future agent), it needs access to a fresh token. **Three options, ranked:**

1. **Token broker on Workers (recommended).** The Worker exposes a private endpoint, e.g. `POST /admin/spotify-token`, behind Cloudflare Access (same pattern as `/app`). grimmauldplace authenticates via a Cloudflare Access service token (Cloudflare's standard pattern for machine-to-machine), hits the endpoint, gets back a short-lived (50-minute) access token. Worker remains the sole owner of the refresh token. Refresh logic stays in one place. Zero changes to the existing OAuth flow.
2. **Replicate the refresh token to a second store.** Worse: now you have two places that can race on the refresh token. Spotify's refresh tokens *do* rotate on use (the new one comes back in the response), so a race causes one runtime to get a 400 invalid_grant. Don't do this.
3. **Run the refresh logic on grimmauldplace, push the access token to KV.** Inverts #1. Possible but means moving the refresh token *off* Workers, which means OAuth callback has to live somewhere new, which is a bigger change than this whole plan.

Pick #1. It's ~30 lines on Workers and keeps the refresh token where it already lives.

### 3.2 D1 access from grimmauldplace

The D1 HTTP API is the load-bearing primitive. Specifics:

- Endpoint: `https://api.cloudflare.com/client/v4/accounts/{account_id}/d1/database/{database_id}/query`.
- Auth: Cloudflare API token, scoped to "D1:Edit" on the specific database. Token lives as a Docker secret on grimmauldplace.
- Rate limits: same as the Worker D1 binding, in practice — D1 doesn't distinguish between binding and HTTP-API consumers. Quota lives at the database level.
- Latency: ~50–150ms per query from grimmauldplace (Atlanta) to D1's nearest region, vs. ~5–20ms from a Worker. For batch jobs this is fine; for a hot path (which we don't have, by design — all moves are batch) it'd be a problem.

**Backup pattern in case D1 HTTP API has an outage:** the constellation builder reads its inputs at the *start* of the run. If the read fails, it logs and exits without writing — yesterday's result stays in place. No partial writes.

### 3.3 Key rotation

Three credentials to track on grimmauldplace:

- Cloudflare API token (D1 access). Rotate every 6 months. Document in `~/stack/etl/README.md`.
- Cloudflare Access service token (Spotify-token-broker access). Rotate yearly per Cloudflare default.
- Spotify client credentials — *don't* live on grimmauldplace under §3.1. Stay on Workers.

Add a simple Uptime Kuma reminder calendar event for each rotation. Not a real rotation system; not worth one for a single-user app.

### 3.4 Home internet uptime as a dependency

Single-failure-domain analysis:

| If grimmauldplace is down for... | Impact |
|----------------------------------|--------|
| Any duration | Public API at chrisbuice.com/surfaces unaffected. Per-minute polling unaffected. MCP unaffected. Dashboard unaffected. |
| 24h | Constellation goes 1 day stale. Visible only on the constellation tab of the showcase. |
| 1 week | Constellation goes a week stale. ETL-derived files unaffected (stale by however long since last `git commit`). Backups skip a week. |
| 1 month | Constellation noticeably stale. Time to either fix the home server or temporarily re-enable the Worker cron. |

**Important:** this asymmetry — public-facing stuff stays on Workers, batch stuff goes home — is the entire reason this plan works. The plan is *robust* to home-server downtime, by design. If we ever propose to move something whose downtime would degrade the public API, that's the moment to push back.

A nice property of leaving the Workers cron entries in place (commented out, not deleted) for the first 30 days: you can flip a flag and route the workload back to Workers if grimmauldplace is having a bad time. Cheap insurance.

### 3.5 Monitoring

Uptime Kuma is already there. Add monitors for:

- ETL last-run mtime (file-mtime monitor or HTTP endpoint monitor against a small status file the container writes).
- Constellation freshness via `/api/health/constellation` on Workers (see §2.2).
- Backup last-run mtime.

That's three new monitors; takes 15 minutes to configure. Not a real observability story; sufficient for a single-user app.

For richer log access: container logs live on grimmauldplace; you can `tail -f` over Tailscale SSH. Don't over-engineer this until something actually goes wrong.

### 3.6 Backups of grimmauldplace itself

The whole `~/stack/` directory is a few hundred MB at most. `tar` it nightly to a USB drive plugged into the MacBook, or to Backblaze. The 98GB SSD is not roomy — keep an eye on `/var/lib/docker` growth, especially if container images aren't pruned.

## 4. Order of operations

Smallest-first, each step proving the next.

### Step 0 — Prove the pattern works (1 evening)

**Smallest viable thing:** stand up a "hello world" container on grimmauldplace that reads a single row from D1 via the HTTP API and writes a row back. No Spotify, no constellation, no business logic. Pick a debug table or `kv` value.

Success criterion: a manual `docker compose run hello` reads and writes D1 from grimmauldplace. If this works, the entire offload plan works. If it fails (auth, network, quota), figure out why before committing to anything bigger.

### Step 1 — D1 backups (half day)

**Why first:** uses the D1 access pattern from Step 0, but doesn't depend on existing code. Failure mode is "no backup happened today," which is bad but not user-visible. Lowest blast radius for catching infrastructure problems.

- New host cron entry, no container needed: `wrangler d1 export spotify-agent-db` weekly to `~/stack/backups/`.
- Uptime Kuma file-mtime monitor.
- Document.

### Step 2 — ETL container + derived-file refresh (1–2 days)

- Move the existing laptop-resident pandas scripts into a Dockerfile-shaped layout in `~/stack/etl/`.
- Bind-mount `data/`. Initial state: `cp` the laptop's `streams.feather` and existing derived files into `~/stack/etl/data/`.
- Host cron: nightly at 2am ET.
- Spotify token broker on Workers (§3.1) for the live-sync extension. This is the *only* code change on the Worker side at this stage.
- Uptime Kuma heartbeat monitor.

**What this proves:** end-to-end flow including Spotify auth from grimmauldplace. After this, the laptop is no longer load-bearing for derived-file freshness — though you can still run scripts there manually for ad-hoc analysis.

### Step 3 — Constellation rebuild migration (2–3 days)

- New container `constellation-builder` running the existing `src/constellation/` code (compiled or via `tsx`).
- Reads `plays`, `track_taste`, `artist_taste` from D1 HTTP API.
- Writes result back via D1 HTTP API.
- Host cron: `0 10 * * *` UTC.
- **Worker side:** comment out (don't delete) the constellation block in `scheduled()`. Keep the `/api/constellation` route untouched — it reads from the same place as before. Add `/api/health/constellation` for staleness monitoring.
- Run for 7 days in parallel-monitor mode (constellation runs on grimmauldplace, public API serves it; Worker's commented-out cron is the rollback button).

**What this proves:** the headroom problem is solved. After 7 days clean, delete the commented-out Worker code.

### Step 4 — Discovery agent migration (2–3 days, optional)

Same pattern as Step 3. Only do this if you want the wins from §2.4 (real RSS parser, more sources, more subrequest budget). Otherwise leave it.

### Step 5 — Re-evaluate the daily 1am ET cron

After Steps 0–4, profile the daily cron with the timing logs added in §2.3. If it's now comfortably under 30s with the constellation gone, leave it. If not, move the slowest phase (probably the taste rebuild) using the same pattern.

## 5. Things explicitly NOT done in this plan

Listed so we don't sleepwalk into them later.

- **No Postgres.** SQLite via D1 + occasional local SQLite for batch reads is sufficient. Adding Postgres to grimmauldplace is a "let's also" trap.
- **No message queue.** No Kafka, no Redis, no RabbitMQ. The cron-and-HTTP pattern is the architecture.
- **No K8s, no Nomad.** Docker Compose is enough for one host with seven containers.
- **No moving the dashboard.** Cloudflare Pages + Access stays. The dashboard is fast and the auth is solved.
- **No moving OAuth or token storage off Workers.** The Spotify refresh token has exactly one home (KV), and the broker pattern in §3.1 keeps it there.
- **No new domain naming.** New containers get Harry Potter subdomains under chrisbuice.com via Cloudflare Tunnel only if they need to be reachable from outside the LAN. The ETL container does *not* need to be reachable; grimmauldplace pulls from D1 and pushes to D1 — it's a client, not a server. Fewer subdomains = fewer attack surfaces.
- **No replacing Workers for `/api/*`.** Pre-decided; restating because it's the load-bearing assumption of the whole plan.

## 6. Open questions

These don't block starting; they need answers before specific steps.

1. **Where to compile the constellation builder code in Step 3?** Option A: dedicated `tsconfig.constellation.json` that builds to `dist-constellation/`, copied into the container at build time. Option B: run via `tsx` in the container, no compile step. **Lean B** — slower startup, one less moving part.
2. **Cloudflare API token scope for D1.** ~~Does "D1:Edit" on a single database give read+write to that database only, or does it leak access to other resources? **Verify before generating the token.**~~ **Resolved (2026-05-02):** D1:Edit is account-wide; no per-database scoping exists in Cloudflare's permission model. Acceptable for our single-database account. Use an account-owned API token (Manage Account → Account API Tokens), not a user-owned token, for service-principal durability — the token survives independently of any individual user's permissions. Token format is `cfat_`-prefixed; passed as `Authorization: Bearer ${token}` with no transformation.
3. **What's the actual current size of `streams.feather`?** Mentioned as 260K rows but not bytes. If it's > a few hundred MB, we should think about whether `tail.feather` lives separately and is unioned at read time, or whether the canonical feather is rewritten nightly. The LISTENING_HISTORY.md "Live API and snapshot freshness" section already prefers the union-at-read pattern; just confirm it's still the right call.
4. **Does grimmauldplace's home internet have a static IP, or is it dynamic-via-tunnel-only?** The plan assumes outbound only (D1 HTTP API, Spotify, ReccoBeats, Last.fm), so dynamic is fine. Confirm there's no inbound dependency I missed.
5. **Container restart policy on power loss.** MacBook Pro lid-closed running on AC. If power blips, does Ubuntu auto-resume? Does Docker auto-start? Does the cloudflared tunnel reconnect? Probably yes to all three but worth verifying once before relying on it for a daily cron.

## 7. Summary

- **Move first:** ETL pandas pipeline (was never on Workers anyway), constellation rebuild (currently bleeding), D1 backups (currently nonexistent).
- **Defer:** taste rebuild, discovery agent — same pattern, but no current pain. Move only if pain develops post-constellation.
- **Never move:** public API, per-minute polling, OAuth, MCP, nightly email, in-session feedback.
- **Pattern:** host cron on grimmauldplace → D1 HTTP API for I/O → Workers stays the sole reader on the request path. No webhooks back to Workers (smaller blast radius). No shared writers to D1 from two runtimes (constellation writes from grimmauldplace; everything else writes from Workers — clean ownership).
- **Token sharing:** Spotify refresh token stays on Workers. grimmauldplace pulls a 50-minute access token via a broker endpoint behind Cloudflare Access service-token auth.
- **Smallest first step:** a hello-world container that reads and writes D1 via HTTP API. Half a day. If that doesn't work, none of this works, and we want to know that before doing real work.
